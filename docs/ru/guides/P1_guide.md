# Part 1 — GNS3 + Docker

## Суть задания

В первой части мы готовим фундамент для всего проекта. Нужно создать два Docker-образа — один будет играть роль обычного компьютера (хоста) в сети, а второй будет маршрутизатором. Затем оба образа нужно импортировать в GNS3, соединить линком и убедиться, что они работают и видят друг друга.

Эти два образа будут использоваться во всех трёх частях проекта. Поэтому важно, чтобы они были собраны правильно с самого начала.

---

## Docker — что это и зачем

Docker — это платформа для запуска приложений в изолированных контейнерах. Контейнер похож на виртуальную машину, но работает совсем иначе: он не эмулирует аппаратуру и не запускает свою операционную систему с нуля. Вместо этого контейнер использует ядро хост-системы, но при этом имеет свою собственную файловую систему, свои процессы и свою сеть. Благодаря этому контейнер запускается за доли секунды (а не за минуты, как виртуальная машина) и потребляет значительно меньше ресурсов.

В контексте нашего проекта каждый контейнер — это отдельное сетевое устройство (хост или маршрутизатор).

### Ключевые понятия Docker

**Dockerfile** — это текстовый файл, в котором описаны шаги по сборке образа. Каждая строка — одна инструкция. Основные инструкции:

- `FROM` — указывает базовый образ, поверх которого мы строим свой. Например, `FROM alpine:latest` берёт за основу Alpine Linux.
- `RUN` — выполняет команду во время сборки. Обычно через `RUN` устанавливаются пакеты.
- `COPY` — копирует файлы с хост-машины внутрь образа.
- `CMD` — команда, которая запускается при старте контейнера.

**Docker image (образ)** — это готовый неизменяемый «снимок» файловой системы, собранный по инструкциям из Dockerfile. Образ нельзя изменить после сборки — его можно только пересобрать.

**Docker container (контейнер)** — это запущенный экземпляр образа. Из одного образа можно запустить сколько угодно контейнеров, и каждый будет работать независимо. Когда контейнер останавливается, все изменения внутри него теряются (если не сохранены в volume).

Собирается образ командой `docker build`, запускается командой `docker run`.

## GNS3 — что это и зачем

GNS3 (Graphical Network Simulator 3) — это программа для моделирования компьютерных сетей. Она позволяет создавать виртуальные топологии: перетаскивать на рабочую область роутеры, свитчи и хосты, соединять их кабелями (линками) и тестировать сетевые конфигурации, как если бы это было реальное оборудование.

GNS3 поддерживает несколько способов запуска устройств:

- Образы Cisco IOS (через эмулятор Dynamips)
- Полноценные виртуальные машины (через QEMU или VirtualBox)
- Docker-контейнеры — **именно этот способ мы используем**

Когда мы добавляем Docker-образ в GNS3, программа создаёт отдельный контейнер для каждого устройства на топологии. GNS3 берёт на себя управление сетевыми интерфейсами контейнеров: создаёт виртуальные Ethernet-адаптеры (eth0, eth1 и т.д.) и соединяет их между собой в соответствии с линками на схеме. Мы можем открыть консоль любого устройства и работать с ним, как будто сидим перед реальным роутером или компьютером.

## Alpine Linux

Alpine — это очень маленький дистрибутив Linux. Полный базовый образ весит около 5 мегабайт. Для сравнения, образ Ubuntu весит больше 70 МБ. Alpine такой маленький потому, что использует musl libc вместо glibc и busybox вместо полного набора GNU-утилит.

Alpine идеально подходит для Docker-контейнеров, где важен малый размер. Пакетный менеджер в Alpine называется `apk` (Alpine Package Keeper).

В нашем проекте Alpine используется как основа для хост-образа. Роутер-образ тоже построен на Alpine — официальный образ FRRouting (`frrouting/frr`) базируется на нём.

## busybox

busybox — это один-единственный исполняемый файл, который заменяет собой десятки стандартных Unix-утилит. Внутри него упакованы `ls`, `cat`, `cp`, `mv`, `grep`, `ping`, `ifconfig`, `sh` и ещё сотни команд. Когда вы вызываете, например, `ls`, busybox смотрит, под каким именем его вызвали, и ведёт себя как соответствующая утилита.

В Alpine Linux busybox встроен по умолчанию — это основа системы. задание явно требует, чтобы busybox (или его эквивалент) был в обоих образах.

## FRRouting (FRR) — что это такое

FRRouting — это набор программ (демонов) для маршрутизации в Linux. Каждый демон отвечает за свой протокол маршрутизации. Вместе они превращают обычный Linux-сервер в полноценный программный маршрутизатор.

Историческая справка: сначала был проект GNU Zebra — один из первых свободных маршрутизаторов для Linux. Потом от него отпочковался Quagga, который стал стандартом на много лет. Затем от Quagga отпочковался FRRouting (FRR), который сейчас является основным и самым активно развиваемым проектом. Именно поэтому в задание упоминаются и zebra, и quagga — это предки FRR.

В Docker Hub есть официальный образ `frrouting/frr`, который мы используем как базу для нашего router-образа.

### Демоны FRR — что запускается внутри контейнера

Когда мы запускаем наш router-контейнер, внутри него стартуют четыре отдельных процесса (демона):

**zebra** — это центральный демон, ядро всей системы FRR. Он управляет сетевыми интерфейсами и таблицей маршрутизации ядра Linux. Все остальные демоны не лезут в ядро напрямую — они общаются с zebra, а zebra уже вносит изменения в маршрутную таблицу. Без zebra ничего не работает.

**bgpd** — демон протокола BGP (Border Gateway Protocol). BGP — это протокол маршрутизации, на котором работает весь Интернет. В первой части проекта bgpd просто запущен и ждёт — по-настоящему мы его сконфигурируем в Part 3, когда будем строить EVPN-фабрику.

**ospfd** — демон протокола OSPF (Open Shortest Path First). OSPF — это протокол для маршрутизации внутри одной сети (в отличие от BGP, который маршрутизирует между сетями). В Part 3 OSPF будет обеспечивать базовую связность между всеми нашими роутерами.

**isisd** — демон протокола IS-IS (Intermediate System to Intermediate System). Это ещё один протокол внутренней маршрутизации, альтернатива OSPF. Крупные провайдеры часто предпочитают IS-IS, потому что он работает не поверх IP, а напрямую поверх L2 (что делает его проще для очень больших сетей). задание требует, чтобы этот демон был запущен.

### vtysh — как управлять FRR

vtysh — это единая командная оболочка для всех демонов FRR. Через неё можно конфигурировать любой из демонов, не переключаясь между ними. Интерфейс очень похож на Cisco IOS CLI.

Основные режимы:
- Просто ввести `vtysh` — открывается интерактивная оболочка
- `vtysh -c "какая-то команда"` — выполнить одну команду и вернуться в bash
- Внутри vtysh: `configure terminal` — перейти в режим конфигурации
- `write memory` — сохранить текущую конфигурацию на диск (чтобы она пережила перезагрузку)
- `show ip route` — посмотреть таблицу маршрутизации
- `show interface brief` — посмотреть список интерфейсов

## Важное требование: никаких IP-адресов по умолчанию

задание прямо говорит: «No IP address should be configured by default». Это означает, что ни в одном из наших Dockerfile не должно быть строк, назначающих IP-адреса на интерфейсы. Адреса назначаются вручную позже, когда мы запускаем контейнер в GNS3 и настраиваем конкретную топологию. Один и тот же образ используется в P1, P2 и P3 с разными адресами.

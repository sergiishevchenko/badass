# Что такое BGP EVPN

## Простыми словами

**EVPN** расшифровывается как **Ethernet VPN** — «Ethernet-сеть через VPN». Описан в RFC 7432.

**BGP EVPN** — это способ сказать всей фабрике дата-центра: «вот этот MAC-адрес живёт за вот этим свитчом», не рассылая broadcast на всю сеть.

Обычный свитч учит MAC-адреса из трафика: увидел фрейм — запомнил, с какого порта он пришёл. EVPN учит MAC-адреса через **BGP**: свитч (у нас VTEP) сам объявляет «у меня появился хост с таким-то MAC», и Route Reflector разносит это объявление остальным.

У нас это главная идея Part 3. VXLAN таскает сами фреймы хостов (data plane). BGP EVPN разносит знания о MAC (control plane). Без EVPN VXLAN пришлось бы настраивать вручную или заливать BUM-трафик вслепую, как в Part 2.

---

## Две плоскости: control plane и data plane

Чтобы не путать протоколы, держи в голове два этажа.

**Data plane** — что реально несёт пользовательские пакеты. Пинг от хоста к хосту летит внутри VXLAN: Ethernet-фрейм заворачивается в UDP и едет по IP-сети роутеров.

**Control plane** — кто кому рассказывает, *куда* эти фреймы слать. В Part 2 это было «remote IP» или multicast-группа. В Part 3 это BGP EVPN: таблица «MAC → VTEP».

Аналогия: data plane — дороги и машины. Control plane — навигатор, который знает адреса. EVPN — навигатор для MAC-адресов.

---

## Зачем EVPN, если уже есть VXLAN

VXLAN умеет только туннель: «заверни L2 в UDP и отправь на такой-то IP». Он сам не знает, у какого VTEP какой хост.

Варианты без EVPN:

1. **Static remote** (Part 2) — в конфиге прописан один сосед. На двух роутерах ок, на пятидесяти — кошмар.
2. **Multicast** (Part 2) — BUM льётся группе. Работает, но в большой сети много лишнего flooding, плюс underlay должен уметь multicast.
3. **Flood-and-learn внутри VXLAN** — как обычный свитч, только через туннели. Плохо масштабируется.

EVPN заменяет «угадай и зафлуди» на «объяви по BGP». VTEP заранее знает: MAC хоста 3 сидит за VTEP `_sshevche-4` (IP 1.1.1.4). Unicast сразу идёт туда.

Согласно заданию: контроллер (у нас RR) учит MAC **автоматически**. IP хосту для этого даже не обязателен — достаточно, что интерфейс поднялся и MAC стал виден на порту.

## Из чего складывается BGP EVPN в нашем проекте

Три слоя:

1. **OSPF (underlay)** — роутеры пингуют loopback друг друга (`1.1.1.1` … `1.1.1.4`).
2. **iBGP + Route Reflector** — VTEP не строят full mesh. Все смотрят в `_sshevche-1`.
3. **Address family `l2vpn evpn`** — по этой BGP-сессии едут не «сети 10.0.0.0/8», а EVPN-маршруты про MAC и VNI.

VXLAN VNI 10 — тот же сегмент, что в Part 2. Отличие: VTEP создаётся с `local <loopback>` и `nolearning`. MAC в data plane специально не учим — ими занимается EVPN.

## Типы маршрутов EVPN (Route Types)

EVPN — это не один вид маршрута. В RFC несколько типов. Нас интересует в первую очередь два.

### Type 3 — Inclusive Multicast Ethernet Tag (IMET)

Смысл одной фразой: «я, VTEP с IP X, участвую в VNI 10 и готов принимать BUM».

Появляется **до хостов**. Как только на VTEP есть VXLAN VNI 10 и включён `advertise-all-vni`, FRR шлёт Type 3 на RR, RR отражает остальным.

Зачем: ARP — это broadcast. Чтобы первый ping вообще случился, VTEP отправителя должен знать, кому слать неизвестный/широковещательный трафик. Type 3 строит список «коллег по VNI».

В FRR смотрят так:

```bash
vtysh -c "show bgp l2vpn evpn route type multicast"
```

Пока хостов нет, Type 2 пустой — это нормально.

### Type 2 — MAC/IP Advertisement

Смысл: «MAC aa:bb:cc:dd:ee:ff (и иногда IP) доступен через VTEP 1.1.1.2 в VNI 10».

Появляется, когда хост ожил на локальном порту (eth1 в bridge). VTEP видит MAC, делает Type 2, отдаёт RR, RR разносит.

Дальше удалённый VTEP кладёт это в свою EVPN/FDB и шлёт известный unicast уже точечно, не flood.

```bash
vtysh -c "show bgp l2vpn evpn route type macip"
vtysh -c "show evpn mac vni 10"
```

IP в Type 2 необязателен. В задании хост поднимают без адреса — Type 2 всё равно должен появиться. Адрес `20.1.1.x` мы ставим только чтобы потом пинговать.

### Другие типы (знать названия, в лабе не настраиваем)

- Type 1 — Ethernet Auto-Discovery (масштабирование, mass withdraw).
- Type 4 — ES (Ethernet Segment), мультихоминг.
- Type 5 — IP Prefix, L3 VPN поверх EVPN.

Для обязательной части проекта достаточно Type 2 и Type 3.

## Как выглядит жизнь пакета с EVPN

Хост `_sshevche-1_host` пингует `_sshevche-3_host`.

1. Ещё нет ARP — host шлёт broadcast «кто 20.1.1.3?».
2. VTEP2 получает фрейм в `br0`.
3. По Type 3 он знает VTEP3 и VTEP4 в VNI 10, инкапсулирует в VXLAN и шлёт BUM им (не «всему интернету»).
4. VTEP4 отдаёт фрейм своему хосту.
5. Ответ ARP идёт обратно. Параллельно (или уже раньше) у VTEP4 есть Type 2 на MAC host_3 — его видят все через RR.
6. Дальше ICMP — обычный unicast внутри VXLAN на VTEP 1.1.1.4.

Человек за хостом ничего этого не видит: для него это один L2-сегмент 20.1.1.0/24.

## Важные команды FRR именно для EVPN

На VTEP:

```
address-family l2vpn evpn
 neighbor 1.1.1.1 activate
 advertise-all-vni
```

- `activate` — по этой сессии включать семейство EVPN, не только «пустой» BGP.
- `advertise-all-vni` — объявить локальные VNI. Без этого Type 3 может не родиться.

На RR вместо advertise-all-vni:

```
neighbor 1.1.1.2 route-reflector-client
```

RR сам не обязан иметь VXLAN. Он почтальон EVPN-маршрутов.

`nolearning` на `vxlan10` — не учить MAC из туннеля по-старому, чтобы не спорить с BGP.

## Связь с соседними терминами

- **MP-BGP** — механизм, которым BGP везёт EVPN (семейство `l2vpn evpn`), а не только IPv4.
- **NLRI** — «полезный груз» UPDATE: что именно объявлено (MAC, VNI, next-hop VTEP).
- **MAC** — то, что EVPN рекламирует Type 2, чтобы свитчи не гадали по flooding.

---

## Резюмируя

BGP EVPN — control plane для VXLAN. VTEP объявляют участие в VNI маршрутами Type 3 и MAC хостов маршрутами Type 2. Route Reflector раздаёт это всем leaf. Датаплейн остаётся VXLAN VNI 10. Поэтому хосты в разных стойках оказываются в одном L2, а MAC находятся сами, без ручной таблицы.

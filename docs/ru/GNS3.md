# Что такое GNS3

## Простыми словами

GNS3 расшифровывается как **Graphical Network Simulator 3** — графический симулятор сетей, третья версия.

Это программа, в которой можно собрать виртуальную сеть на экране: расставить роутеры, свитчи и компьютеры, соединить их «кабелями» и настраивать так, будто это настоящее железо. Не нужно покупать стойку Cisco и тянуть провода. Всё происходит на одном компьютере (у нас — внутри виртуальной машины).

В проекте BADASS GNS3 — это «лаборатория». Docker даёт нам образы устройств (хост и маршрутизатор), а GNS3 собирает из них топологию: кто с кем соединён, какой интерфейс куда смотрит, как открыть консоль.

---

## Зачем вообще нужен симулятор сети

Настоящую сеть из семи устройств собрать тяжело:

- нужно железо или много виртуальных машин;
- каждый кабель, порт и ошибка в IP занимает время;
- эксперимент «оторвать линк и посмотреть, что будет» на реальном оборудовании неудобен.

GNS3 решает это так: устройства — это процессы (у нас Docker-контейнеры), а кабели — виртуальные линки внутри программы. Можно:

- нарисовать схему;
- запустить все узлы одной кнопкой;
- зайти в консоль любого устройства;
- перехватить трафик (tcpdump / Wireshark);
- сохранить проект и отдать его другому человеку.

Для данного проекта это стандартный инструмент: проверяющий на защите открывает тот же `.gns3project` и видит ту же топологию.

## Из чего состоит GNS3

GNS3 — это не одна кнопка, а связка из двух частей.

### GNS3 GUI (графический интерфейс)

Это окно, которое вы видите:

- рабочая область (холст), куда перетаскивают устройства;
- панели с шаблонами (роутеры, хосты, облака, свитчи);
- меню File / Edit / Preferences;
- кнопки Start / Stop / Console.

GUI сам по себе почти ничего не запускает. Он только рисует схему и отправляет команды серверу: «создай контейнер», «соедини eth0 с eth1», «открой консоль».

### GNS3 Server

Это фоновый процесс, который реально создаёт устройства и сеть.

Когда вы кладёте на схему Docker-роутер и жмёте Start, сервер:

1. просит Docker запустить контейнер из образа;
2. создаёт виртуальные сетевые интерфейсы;
3. соединяет их согласно линкам на схеме;
4. даёт GUI доступ к консоли.

В нашем проекте GUI и Server обычно крутятся **на одной и той же VM**. Можно и сложнее: GUI на ноутбуке, а тяжёлая работа — на отдельной GNS3 VM. Для BADASS достаточно локального сервера на той же машине, где установлен Docker.

Проверка, что сервер жив: GNS3 запускается без ошибки подключения, в статусе видно, что local server работает.

## Как GNS3 работает с Docker

Это центральная идея Part 1.

1. Вы собираете образ: `docker build -t dmiasnik-router ...`
2. В GNS3 создаёте **шаблон** (template): «это устройство использует образ `dmiasnik-router`, у него N сетевых адаптеров».
3. Перетаскиваете шаблон на холст. Появляется **узел** (node) — экземпляр шаблона.
4. Соединяете узлы линками.
5. Жмёте Start. GNS3 Server говорит Docker: запусти контейнер из этого образа.
6. Для каждого адаптера шаблона контейнер получает интерфейс: `eth0`, `eth1`, `eth2`...
7. Линк на схеме = виртуальный кабель между `ethX` одного контейнера и `ethY` другого.
8. Двойной клик / Console открывает shell внутри контейнера.

С точки зрения Linux внутри контейнера это обычный сетевой интерфейс. Команды те же: `ip addr`, `ping`, `vtysh`. GNS3 только «подвёл кабели».

Важно: **GNS3 не назначает IP сам**. Subject прямо требует: в образах нет IP по умолчанию. Адреса вы прописываете руками конфигами из `P1/`, `P2/`, `P3/`.

## Основные понятия интерфейса

### Проект (Project)

Один файл/папка со схемой. У нас три отдельных проекта: P1, P2, P3. Не стоит пихать все части на один холст — на защите путаница, да и subject просит три папки.

### Шаблон (Template / Appliance)

Заготовка устройства: какой Docker-образ, сколько адаптеров, какая консоль, какая стартовая команда. Шаблон создаётся один раз в Preferences. На холст можно кинуть сколько угодно копий.

Пример: шаблон `dmiasnik-router` с 4 адаптерами. Из него в P3 получаются `_sshevche-1`, `_sshevche-2`, `_sshevche-3`, `_sshevche-4` — четыре разных контейнера из одного образа.

### Узел (Node)

Конкретное устройство на схеме. У него есть имя (label), которое **должно содержать логин**: `_dmiasnik-2`, `_sshevche-1`. Имя на схеме и имя Docker-образа — разные вещи.

### Адаптер (Adapter)

Сетевая карта узла. Adapter 0 → обычно `eth0`, adapter 1 → `eth1` и так далее.

Если в шаблоне указано 1 adapter, а в Part 3 Route Reflector должен иметь eth0, eth1 и eth2 — третьего интерфейса просто не будет. Поэтому для роутера сразу ставят несколько адаптеров (у нас в SETUP — 4).

### Линк (Link)

Кабель между двумя адаптерами. В GNS3 это не «магия маршрутизации», а L2-соединение: фреймы с одного eth попадают на другой, как будто патч-корд вставлен в два порта.

Перепутать eth0 и eth1 на схеме — самая частая причина, почему конфиг «правильный», а ping не идёт: скрипт вешает VXLAN на eth0, а кабель к соседу воткнут в eth1.

### Консоль (Console)

Окно, в котором вы сидите внутри устройства. Типы:

- **docker** — по сути `docker exec` в контейнер, удобный shell;
- **telnet** — классика GNS3, подключение к псевдотерминалу.

Для Linux/Docker обычно проще console type `docker`.

### Start / Stop / Suspend

- **Start** — контейнер запускается, интерфейсы появляются, демоны FRR стартуют (если так задумано в образе).
- **Stop** — контейнер останавливается. Изменения внутри (назначенные IP, vxlan, конфиг vtysh) часто **пропадут**, если их не сохранили так, как задумано образом. После Stop обычно нужно применить скрипты заново — либо полагаться на portable export, который сохраняет состояние проекта.
- **Reload** — перезапуск узла.

### Capture / Wireshark

На линк можно повесить захват пакетов. Для VXLAN полезно смотреть UDP 4789. В контейнере то же самое делает `tcpdump`.

## Portable project — то, что сдаётся

По заданию требуется не «скриншот схемы», а файл:

```text
P1/P1.gns3project
P2/P2.gns3project
P3/P3.gns3project
```

Это **ZIP-архив**. Меню: **File → Export portable project**.

«Portable» значит: внутри лежат описание топологии **и базовые образы**, чтобы на другом компьютере (компьютер группы на защите) проект открылся без ручной пересборки всего с нуля.

Проверка:

```bash
file P1/P1.gns3project
# должно быть: Zip archive data
```

Если экспортировать «без images», проверяющий может не смочь запустить узлы.

Рядом с ZIP в той же папке лежат текстовые конфиги устройств (`_dmiasnik-2`, `_sshevche-1` и т.д.) с пояснениями — это отдельное требование subject.

## Типичный цикл работы в GNS3 для BADASS

1. Собрать Docker-образы на VM.
2. Создать шаблоны host и router в Preferences.
3. File → New blank project (например P2).
4. Перетащить нужное число узлов, переименовать с логином.
5. Соединить адаптеры строго по схеме (eth0 underlay, eth1 к хосту и т.д.).
6. Start all.
7. Открыть консоль каждого узла, выполнить конфиг.
8. Проверить ping / OSPF / BGP / tcpdump.
9. File → Export portable project в папку `P1/`, `P2/` или `P3/`.

GNS3 не «настроит VXLAN за вас». Он только даёт устройства и кабели. Вся логика — в командах `ip`, `brctl` и `vtysh`.

---

## Резюме

GNS3 — графический симулятор сетей. Мы рисуем топологию, а сервер GNS3 запускает каждое устройство как Docker-контейнер и соединяет их виртуальными Ethernet-линками. IP и протоколы настраиваем внутри контейнеров вручную. Для сдачи экспортируем portable project — ZIP со схемой и образами.

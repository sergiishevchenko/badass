# Part 3 — BGP EVPN

## Суть задания

В третьей части мы строим мини-дата-центр. У нас 7 устройств: один центральный роутер (Route Reflector), три leaf-роутера (VTEP) и три хоста. Задача — сделать так, чтобы хосты, подключённые к разным VTEP, могли общаться друг с другом через VXLAN-туннель, причём MAC-адреса хостов обнаруживались автоматически, без ручной настройки.

Для этого используется связка из трёх технологий:
- **OSPF** — обеспечивает базовую IP-связность между всеми роутерами (underlay)
- **BGP EVPN** — автоматически распространяет информацию о MAC-адресах хостов (control plane)
- **VXLAN** — передаёт данные хостов через IP-сеть (data plane)

---

## BGP — протокол, на котором работает Интернет

**BGP** расшифровывается как **Border Gateway Protocol** и описан в RFC 4271.

Чтобы понять BGP, нужно представить, как устроен Интернет. Интернет — это не одна большая сеть, а тысячи отдельных сетей (провайдеров, дата-центров, университетов), объединённых между собой. Каждая такая сеть называется **автономная система (AS)** и имеет свой номер (ASN).

BGP — это протокол, через который автономные системы обмениваются информацией о маршрутах. Когда вы заходите на сайт, ваш пакет может пройти через десяток разных AS, и на каждом стыке именно BGP решает, куда передать пакет дальше.

BGP работает поверх TCP на порту 179. Два BGP-роутера устанавливают между собой TCP-соединение (это называется **peering** или **BGP-сессия**), и через него обмениваются маршрутами. Когда один роутер узнаёт новый маршрут, он отправляет его соседу в специальном сообщении UPDATE.

### AS — автономная система

**AS** расшифровывается как **Autonomous System**. Это группа IP-сетей, находящихся под единым административным управлением. У каждой AS есть номер — **ASN** (Autonomous System Number).

Например, у Google ASN 15169, у Cloudflare — 13335, у EPFL — 2831. В нашем проекте мы используем ASN 65000 — это номер из так называемого «приватного» диапазона (64512–65534), который предназначен для внутреннего использования.

### iBGP и eBGP — внутренний и внешний BGP

Существуют два режима работы BGP:

**eBGP (external BGP)** — это BGP между разными автономными системами. Когда роутер провайдера A (AS 100) общается с роутером провайдера B (AS 200) по BGP — это eBGP. Именно eBGP обеспечивает маршрутизацию в Интернете.

**iBGP (internal BGP)** — это BGP внутри одной автономной системы. Все роутеры имеют одинаковый ASN. В нашем проекте все четыре роутера находятся в AS 65000, поэтому между ними работает iBGP.

Зачем нужен iBGP, если внутри сети уже есть OSPF? Потому что OSPF — это протокол для IP-маршрутизации (Layer 3). А нам нужно передавать не IP-маршруты, а информацию о MAC-адресах (EVPN). OSPF так не умеет, а BGP — умеет, благодаря расширению MP-BGP.

### Проблема iBGP: full mesh

У iBGP есть одно важное правило (anti-loop mechanism): маршрут, полученный от одного iBGP-соседа, нельзя передавать другому iBGP-соседу. Это правило предотвращает зацикливание маршрутов, но создаёт проблему: чтобы все роутеры знали все маршруты, каждый роутер должен быть напрямую соединён BGP-сессией с каждым другим. Это называется **full mesh**.

Если у вас 4 роутера — нужно 6 сессий. Если 10 — нужно 45. Если 100 — нужно 4950. Это не масштабируется.

Решение — Route Reflector.

---

## Route Reflector (RR) — решение проблемы full mesh

**Route Reflector** (дословно — «отражатель маршрутов») — это специальный BGP-роутер, который нарушает правило iBGP и имеет право передавать маршруты от одного клиента другому.

Как это работает: вместо full mesh все роутеры пирятся только с RR. Когда VTEP_2 отправляет маршрут на RR, тот «отражает» его на VTEP_3 и VTEP_4. VTEP_3 и VTEP_4 не нужно пириться друг с другом — достаточно связи с RR.

В нашем проекте `_sshevche-1` выполняет роль Route Reflector. Остальные три роутера (`_sshevche-2`, `_sshevche-3`, `_sshevche-4`) — его клиенты. В конфигурации это задаётся командой `route-reflector-client`:

```
neighbor 1.1.1.2 route-reflector-client
```

Вместо 6 BGP-сессий (full mesh для 4 роутеров) нам нужно всего 3 (каждый VTEP ↔ RR).

## MP-BGP — расширение BGP для разных протоколов

**MP-BGP** расшифровывается как **Multi-Protocol BGP** и описан в RFC 4760.

Стандартный BGP (RFC 4271) умеет переносить только IPv4 unicast маршруты. Но мир не ограничивается IPv4. Нужно передавать маршруты для IPv6, для VPN, для EVPN и много чего ещё.

MP-BGP добавляет в BGP концепцию **address family** (семейство адресов). Каждое семейство — это отдельный «канал» внутри BGP-сессии:

- `ipv4 unicast` — обычные IPv4-маршруты
- `ipv6 unicast` — IPv6-маршруты
- `l2vpn evpn` — EVPN-маршруты (информация о MAC-адресах) — **это то, что мы используем**

В конфигурации FRR семейство адресов задаётся блоком `address-family`:

```
address-family l2vpn evpn
 neighbor 1.1.1.1 activate
 advertise-all-vni
exit-address-family
```

## EVPN — автоматическое обнаружение MAC-адресов

**EVPN** расшифровывается как **Ethernet VPN** и описан в RFC 7432.

В обычной L2-сети (без EVPN) свитчи изучают MAC-адреса через **flooding + learning**: когда приходит фрейм с неизвестным MAC-адресом назначения, свитч рассылает его на все порты (flooding). Когда ответ приходит обратно, свитч запоминает, на каком порту находится MAC отправителя (learning). Это работает, но плохо масштабируется в больших сетях с тысячами хостов.

EVPN подходит к задаче совсем по-другому. Вместо изучения MAC через data plane (реальные пакеты), EVPN передаёт информацию о MAC-адресах через **control plane** (BGP). Когда VTEP обнаруживает новый MAC на своём локальном порту, он формирует BGP-маршрут и отправляет его всем остальным VTEP через Route Reflector. Теперь все VTEP знают, где находится этот MAC, ещё до того, как получат от него хоть один пакет.

### NLRI — что передаётся внутри BGP

**NLRI** расшифровывается как **Network Layer Reachability Information**. Это общий термин BGP для данных о достижимости сетей. В контексте EVPN NLRI содержит информацию о MAC-адресах и IP-адресах хостов: какой MAC на каком VTEP, какой VNI используется и т.д.

## EVPN Route Types — типы маршрутов

EVPN определяет несколько типов маршрутов (Route Types). Каждый тип несёт свою информацию. В нашем проекте используются два типа:

### Type 2 — MAC/IP Advertisement Route

Маршрут Type 2 объявляет конкретный MAC-адрес (и, опционально, IP-адрес) конечного хоста.

Разберём на примере: хост с MAC-адресом `aa:bb:cc:dd:ee:ff` подключается к VTEP_2. VTEP_2 обнаруживает этот MAC на своём локальном интерфейсе и создаёт BGP-маршрут Type 2 со следующим смыслом: «MAC aa:bb:cc:dd:ee:ff доступен через меня (VTEP IP 1.1.1.2) в VNI 10». VTEP_2 отправляет этот маршрут на Route Reflector. RR отражает маршрут на VTEP_3 и VTEP_4. Теперь все три VTEP знают, что этот MAC находится за VTEP_2. Когда VTEP_4 получит фрейм, адресованный этому MAC, он сразу знает, куда его отправить — не нужно делать flooding.

Type 2 маршруты создаются динамически — они появляются, когда хост подключается, и исчезают, когда хост уходит.

### Type 3 — Inclusive Multicast Ethernet Tag Route (IMET)

Маршрут Type 3 говорит: «я, VTEP с IP X.X.X.X, участвую в VNI 10 и готов принимать BUM-трафик».

Type 3 маршруты создаются автоматически при настройке VNI на VTEP, **ещё до подключения каких-либо хостов**. Их задача — построить «дерево» для рассылки BUM-трафика. Когда хост отправляет broadcast (например, ARP-запрос), его VTEP должен знать, каким другим VTEP переслать этот broadcast. Type 3 маршруты дают эту информацию.

Поэтому в проекте сначала должны появиться Type 3 маршруты (от всех VTEP), и только потом, когда подключаются хосты, — Type 2 маршруты.

## OSPF — фундамент нашей сети

**OSPF** расшифровывается как **Open Shortest Path First** и описан в RFC 2328. Это протокол внутренней маршрутизации (**IGP** — Interior Gateway Protocol), который работает внутри одной автономной системы.

OSPF находит кратчайшие пути между роутерами. Каждый роутер знает полную карту сети (topology) и самостоятельно вычисляет лучший маршрут до каждой подсети.

В нашем проекте OSPF играет роль **underlay** — он обеспечивает IP-связность между loopback-адресами всех роутеров. Без OSPF роутеры не смогут достучаться до loopback-адресов друг друга, а значит BGP-сессии (которые строятся через loopback) не установятся.

### Как работает OSPF

Когда роутер включается и на его интерфейсах настроен OSPF, он начинает отправлять Hello-пакеты. Соседние роутеры, получив Hello, отвечают тем же. Если параметры совпадают (area, таймеры), роутеры становятся **соседями (neighbors)** и начинают обмениваться информацией о своих сетях.

Процесс установления соседства проходит через несколько стадий, конечная — **Full**. Когда вы видите `Full` в выводе `show ip ospf neighbor` — значит роутеры полностью синхронизировали свои базы данных и маршрутизация работает.

### Area — логическое разделение

OSPF делит сеть на **зоны (areas)**. Каждая зона — это группа роутеров, которые обмениваются детальной информацией о топологии только между собой. Между зонами передаётся только сводная информация.

В нашем проекте все роутеры находятся в **Area 0** (она же backbone area). Area 0 — это обязательная центральная зона, через которую проходит весь трафик между другими зонами. Поскольку у нас всего 4 роутера, достаточно одной зоны.

### IGP — общий термин

**IGP** расшифровывается как **Interior Gateway Protocol**. Это общее название для протоколов маршрутизации внутри одной AS. OSPF — это IGP. IS-IS — тоже IGP. RIP — тоже, хотя устаревший. Для underlay в проекте используется OSPF.

---

## IS-IS — зачем упоминается

**IS-IS** расшифровывается как **Intermediate System to Intermediate System**. Это ещё один IGP-протокол, альтернатива OSPF. Его особенность — он работает не поверх IP, а напрямую поверх Layer 2. Крупные провайдеры (например, уровня Tier-1) часто предпочитают IS-IS именно за это.

В проекте демон `isisd` запущен, маршруты через него не строятся. Для маршрутизации используется OSPF: его проще настроить, и для этой топологии его хватает.

---

## Loopback — стабильный адрес роутера

**Loopback** — это виртуальный сетевой интерфейс, который не привязан ни к какому физическому порту. Главное свойство loopback — он всегда в состоянии UP, пока роутер работает. Физический интерфейс может упасть (кабель выдернули, порт сгорел), но loopback будет работать, пока есть хоть один активный физический интерфейс.

Именно поэтому BGP-сессии строятся через loopback, а не через физические интерфейсы. Если BGP-сессия построена через eth0, а eth0 падает — сессия разрывается, даже если есть альтернативный путь через eth1. Если сессия построена через loopback — она живёт, пока OSPF может найти хоть какой-то маршрут до loopback-адреса соседа.

В нашем проекте loopback-адреса:
- `_sshevche-1` (RR): **1.1.1.1**/32
- `_sshevche-2` (VTEP): **1.1.1.2**/32
- `_sshevche-3` (VTEP): **1.1.1.3**/32
- `_sshevche-4` (VTEP): **1.1.1.4**/32

Маска `/32` означает, что это единственный адрес (не подсеть). OSPF объявляет эти адреса, и все роутеры знают, как до них добраться.

В VXLAN loopback используется ещё и как **VTEP source IP** — IP-адрес, от имени которого VTEP отправляет VXLAN-пакеты.

## Ключевые команды FRR — что они значат

### update-source lo

В BGP по умолчанию пакеты отправляются с IP-адреса того физического интерфейса, через который они выходят. Команда `update-source lo` говорит: «отправляй BGP-пакеты с IP-адреса loopback». Это работает, потому что OSPF обеспечивает маршрут до loopback-адреса соседа.

```
neighbor 1.1.1.1 update-source lo
```

### no bgp default ipv4-unicast

По умолчанию FRR автоматически включает address-family `ipv4 unicast` для каждого BGP-соседа. Нам это не нужно — мы используем BGP только для EVPN (`l2vpn evpn`). Команда `no bgp default ipv4-unicast` отключает автоматическое включение IPv4, чтобы мы явно активировали только то, что нужно.

### advertise-all-vni

Эта команда включается на каждом VTEP. Она говорит FRR: «посмотри, какие VNI настроены на этом роутере, и объяви их через EVPN». Без этой команды VTEP не будет создавать Type 3 маршруты и фактически не будет участвовать в EVPN. Именно благодаря этой команде при старте VTEP автоматически создаётся Type 3 маршрут для VNI 10.

### nolearning

Когда мы создаём VXLAN-интерфейс в Part 3, мы добавляем флаг `nolearning`:

```bash
ip link add vxlan10 type vxlan id 10 dstport 4789 local 1.1.1.2 nolearning
```

Что это значит: обычно VXLAN-интерфейс сам изучает MAC-адреса из проходящего трафика (data-plane learning) — примерно так же, как обычный свитч. Но в нашем случае MAC-адреса передаются через BGP EVPN (control-plane learning). Если оставить оба механизма включёнными, они могут конфликтовать: data plane запишет одно, control plane — другое. Поэтому data-plane learning отключается.

В Part 2 мы не использовали `nolearning`, потому что там не было EVPN — MAC-адреса изучались обычным способом.

### router-id

**Router ID** — это уникальный идентификатор роутера, который используется в BGP и OSPF для различения роутеров. Обычно в качестве router-id берут IP-адрес loopback-интерфейса. В нашем проекте router-id = loopback IP.

## Leaf-Spine — архитектура дата-центра

В реальных дата-центрах используется архитектура **Leaf-Spine** (лист-хребет), также известная как **CLOS topology**:

**Leaf (лист)** — это коммутатор доступа, к которому подключаются серверы (хосты). Каждый сервер подключён к одному (или двум для отказоустойчивости) leaf-коммутатору. В нашем проекте leaf — это VTEP (`_sshevche-2`, `_sshevche-3`, `_sshevche-4`).

**Spine (хребет)** — это коммутатор агрегации, к которому подключены все leaf. Spine не подключает серверы напрямую — он только связывает leaf между собой. В полноценном дата-центре обычно 2–4 spine, и каждый leaf подключён к каждому spine.

В нашем проекте топология упрощена: `_sshevche-1` (RR) выполняет роль единственного spine, к которому подключены все три leaf.

### IP-адресация

**Underlay (физические линки между роутерами):**

| Линк | Подсеть | Роутер 1 | Роутер 2 |
|------|---------|----------|----------|
| RR ↔ VTEP2 | 10.1.1.0/30 | .1 (eth0) | .2 (eth0) |
| RR ↔ VTEP3 | 10.1.1.4/30 | .5 (eth1) | .6 (eth0) |
| RR ↔ VTEP4 | 10.1.1.8/30 | .9 (eth2) | .10 (eth0) |

Подсети /30 — это минимальный размер для point-to-point линка (4 адреса: сеть, два хоста, broadcast).

**Loopback-адреса:**

| Устройство | Роль | Loopback |
|---|---|---|
| _sshevche-1 | Route Reflector | 1.1.1.1/32 |
| _sshevche-2 | VTEP (leaf) | 1.1.1.2/32 |
| _sshevche-3 | VTEP (leaf) | 1.1.1.3/32 |
| _sshevche-4 | VTEP (leaf) | 1.1.1.4/32 |

**Overlay (хосты в VNI 10):**

| Хост | IP | Подключён к VTEP |
|---|---|---|
| _sshevche-1_host | 20.1.1.1/24 | _sshevche-2 |
| _sshevche-2_host | 20.1.1.2/24 | _sshevche-3 |
| _sshevche-3_host | 20.1.1.3/24 | _sshevche-4 |

Все три хоста находятся в одном L2-сегменте (VNI 10) и могут общаться друг с другом напрямую по MAC.

## Как всё работает вместе — четыре этапа

### Этап 1: OSPF поднимает underlay

Когда мы запускаем все роутеры и применяем конфиги, первым делом начинает работать OSPF. Роутеры отправляют Hello-пакеты на своих интерфейсах, обнаруживают соседей и обмениваются информацией о подсетях.

Через примерно 10 секунд OSPF завершает синхронизацию. Теперь каждый роутер знает маршруты до всех подсетей и, что самое важное, до всех loopback-адресов.

На этом этапе можно проверить:
```bash
vtysh -c "show ip ospf neighbor"
```
Должно быть 3 соседа (на RR) или 1 сосед (на каждом VTEP), все в состоянии `Full`.

```bash
ping 1.1.1.1    # с любого VTEP — loopback RR должен отвечать
ping 1.1.1.4    # с RR — loopback VTEP4 должен отвечать
```

### Этап 2: BGP устанавливает EVPN-сессии

После того как OSPF обеспечил связность loopback-адресов, BGP может установить сессии. Каждый VTEP устанавливает iBGP-сессию с RR через loopback (поэтому OSPF должен работать первым — без маршрута до loopback сессия не поднимется).

Как только BGP-сессии поднялись, каждый VTEP отправляет **Type 3 маршрут**: «я (1.1.1.X) участвую в VNI 10». RR получает эти маршруты и отражает их всем клиентам. Теперь каждый VTEP знает обо всех остальных VTEP в VNI 10.

На этом этапе хосты ещё не подключены, поэтому Type 2 маршрутов нет — и это нормально.

```bash
vtysh -c "show bgp summary"
```
На RR должно быть 3 peer в состоянии `Estab` (established).

```bash
vtysh -c "show bgp l2vpn evpn route type multicast"
```
Должны быть видны Type 3 маршруты от каждого VTEP.

### Этап 3: Хосты подключаются — появляются Type 2

Когда мы поднимаем интерфейс на хосте (даже без назначения IP), VTEP обнаруживает его MAC-адрес через свой локальный bridge-порт и создаёт **Type 2 маршрут**.

Например, мы поднимаем `_sshevche-1_host`. VTEP `_sshevche-2` видит новый MAC на eth1, создаёт Type 2 маршрут: «MAC xx:xx:xx:xx:xx:xx доступен через VTEP 1.1.1.2 в VNI 10». Отправляет его на RR. RR отражает на `_sshevche-3` и `_sshevche-4`.

Подключаем `_sshevche-3_host`. VTEP `_sshevche-4` создаёт второй Type 2 маршрут. RR отражает его всем.

Теперь все VTEP знают расположение обоих хостов.

```bash
vtysh -c "show bgp l2vpn evpn route type macip"
```
Должны быть видны Type 2 маршруты — по одному на каждый подключённый хост.

### Этап 4: Ping — проверяем, что всё работает

Назначаем IP-адреса хостам (20.1.1.1 и 20.1.1.3) и пингуем.

Когда `_sshevche-1_host` (20.1.1.1) пингует `_sshevche-3_host` (20.1.1.3), вот что происходит:

1. host_1 отправляет ARP-запрос: «кто 20.1.1.3?» (broadcast на ff:ff:ff:ff:ff:ff)
2. Фрейм попадает через eth1 в bridge br0 на VTEP_2
3. Bridge передаёт фрейм на vxlan10
4. VTEP_2 знает из Type 3 маршрутов, что VTEP_3 и VTEP_4 тоже в VNI 10. Он инкапсулирует фрейм в VXLAN (VNI 10) и отправляет обоим (BUM flood)
5. VTEP_4 получает VXLAN-пакет, декапсулирует его и передаёт через bridge → eth1 к host_3
6. host_3 отвечает на ARP со своим MAC-адресом
7. VTEP_4 теперь знает MAC host_3 и создаёт Type 2 маршрут (если ещё не создал)
8. Ответ идёт обратно: host_3 → VTEP_4 → (VXLAN) → VTEP_2 → host_1
9. Теперь host_1 знает MAC host_3 и отправляет ICMP echo request (ping)
10. Ping проходит по маршруту: host_1 → VTEP_2 → (VXLAN VNI 10 через underlay) → VTEP_4 → host_3

## Конфигурация FRR — разбор по строкам

### Route Reflector (_sshevche-1)

**OSPF-часть:**
```
router ospf
 network 10.1.1.0/30 area 0       # линк к VTEP2 (eth0)
 network 10.1.1.4/30 area 0       # линк к VTEP3 (eth1)
 network 10.1.1.8/30 area 0       # линк к VTEP4 (eth2)
 network 1.1.1.1/32 area 0        # свой loopback — чтобы VTEP знали маршрут до него
```

Каждая строка `network ... area 0` говорит OSPF: «включи этот интерфейс в процесс OSPF в зоне 0 и объяви его подсеть соседям».

**BGP-часть:**
```
router bgp 65000                    # запускаем BGP в AS 65000
 bgp router-id 1.1.1.1             # наш router ID = IP loopback
 no bgp default ipv4-unicast       # не включать IPv4 автоматически
```

```
 neighbor 1.1.1.2 remote-as 65000  # VTEP2: та же AS = iBGP
 neighbor 1.1.1.2 update-source lo # отправлять BGP с loopback IP
 neighbor 1.1.1.3 remote-as 65000  # VTEP3
 neighbor 1.1.1.3 update-source lo
 neighbor 1.1.1.4 remote-as 65000  # VTEP4
 neighbor 1.1.1.4 update-source lo
```

```
 address-family l2vpn evpn                  # блок настроек EVPN
  neighbor 1.1.1.2 activate                # включить EVPN для VTEP2
  neighbor 1.1.1.2 route-reflector-client  # VTEP2 — наш RR-клиент
  neighbor 1.1.1.3 activate
  neighbor 1.1.1.3 route-reflector-client
  neighbor 1.1.1.4 activate
  neighbor 1.1.1.4 route-reflector-client
 exit-address-family
```

`activate` — включить обмен EVPN-маршрутами с этим соседом.
`route-reflector-client` — разрешить отражать маршруты от этого клиента другим клиентам.

### VTEP (_sshevche-2)

**OSPF-часть:**
```
router ospf
 network 10.1.1.0/30 area 0       # линк к RR
 network 1.1.1.2/32 area 0        # свой loopback
```

**BGP-часть:**
```
router bgp 65000
 bgp router-id 1.1.1.2
 no bgp default ipv4-unicast

 neighbor 1.1.1.1 remote-as 65000  # RR
 neighbor 1.1.1.1 update-source lo

 address-family l2vpn evpn
  neighbor 1.1.1.1 activate
  advertise-all-vni                 # объявлять все VNI через EVPN
 exit-address-family
```

Обратите внимание: у VTEP нет `route-reflector-client`, зато есть `advertise-all-vni`. У RR наоборот: есть `route-reflector-client`, но нет `advertise-all-vni` (потому что на RR нет VXLAN).
